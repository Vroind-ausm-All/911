01Warum das zählt

Geschwindigkeit ist
keine Sicherheit.

Ein Sprachmodell schreibt Code, der funktioniert. Funktionieren heißt: der glückliche Pfad geht durch. Sicherheit heißt: alle anderen Pfade gehen nicht durch.

Genau diese anderen Pfade stehen selten im Prompt. Niemand schreibt „und bitte so, dass fremde Nutzer meine Rechnungen nicht lesen können“ — man schreibt „bau mir eine Rechnungsübersicht“. Das Modell liefert exakt das Bestellte. Die Lücke entsteht nicht im Modell, sondern zwischen Bestellung und Erwartung.

Dazu kommt ein Verantwortungs­problem: Wer den Code nie gelesen hat, kann seine Fehler nicht sehen — haftet aber trotzdem für sie. Datenschutz, Kundendaten, Zahlungsverkehr: Der Betreiber ist die Person mit dem Domainnamen, nicht das Modell.

02Ursachen

Warum Modelle
diese Fehler wiederholen.

U—01

Trainingsdaten sind Tutorials

Der öffentliche Beispielcode der Welt ist Demo-Code: kurz, ohne Auth, ohne Fehlerbehandlung, mit admin/admin. Ein Modell, das darauf trainiert wurde, hält Demo-Code für Normalcode.

U—02

Belohnt wird „läuft“

Rückmeldung bekommt das Modell dafür, dass etwas erscheint und keine Konsole rot wird. Eine fehlende Autorisierungs­prüfung erzeugt keinen Fehler — sie erzeugt nur Zugriff.

U—03

Kein Kontext, kein Angreifer

Im Prompt steht das Feature, nicht die Bedrohung. Ohne „wer darf das sehen, wer nicht“ gibt es keinen Grund, eine Prüfung einzubauen. Weggelassene Sicherheit sieht aus wie sauberer Code.

U—04

Sicherer Ton, unsicherer Code

Die Erklärung klingt souverän, egal wie der Code aussieht. Diese Souveränität ersetzt beim Lesen das Review — man prüft nicht, was ohnehin überzeugend erklärt wurde.

Die Frage ist nicht,
ob die KI Code schreiben kann.
Sondern ob du ihn lesen kannst.

Praktische Konsequenz: Jede generierte Datei braucht ein Minimum an menschlichem Durchgang. Nicht Zeile für Zeile — aber an den drei Stellen, an denen Vertrauen entsteht: Eingang (was kommt von außen rein), Grenze (wer darf was), Ausgang (was geht nach außen raus).

Das Handbuch unten ist genau nach diesen Stellen sortierbar.

18 / 18
Kein Eintrag passt zu diesem Filter.

Vollständigkeit ist hier ein Anspruch an die Häufigkeit, nicht an die Welt: Das sind die Fehler, die in generiertem Web-Code regelmäßig auftauchen. Sie ersetzen keinen Penetrationstest — sie sorgen dafür, dass ein Penetrationstest nicht mit den Grundlagen anfangen muss.

04Vor dem Deploy

Zwölf Punkte.
Fünf Minuten.

0/12

Der Haken bleibt im Browser gespeichert (localStorage), verlässt dieses Gerät nicht und wird nirgendwohin gesendet.

Zwölf grüne Haken heißen nicht „sicher“. Sie heißen: die Fehler, die in generiertem Code am häufigsten vorkommen, sind ausgeschlossen. Alles darüber hinaus — Geschäftslogik, Zahlungsflüsse, Rechteketten — braucht ein echtes Review.

Guter Rhythmus: Der Check läuft nicht einmal vor dem Launch, sondern nach jeder größeren generierten Änderung. KI-Code wächst schnell — und mit ihm die Fläche.

05Prompt-Bausteine

Sicherheit
mitbestellen.

Der günstigste Zeitpunkt für eine Sicherheitsprüfung ist der Prompt. Diese vier Bausteine lassen sich an jede Anfrage anhängen — sie verschieben die Voreinstellung des Modells von „läuft“ auf „hält stand“.
